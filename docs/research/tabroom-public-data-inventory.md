# Tabroom public data inventory

## Executive summary

DebateOS can build a tournament participation and pairing warehouse from public JSON. For Harvard 40923, anonymous REST provided tournament and invitation metadata and a structured Open event field with 95 entries, each matched by entry ID in the bulk export. The bulk export supplied three divisions, 41 tournament schools, 13 timeslots, student rosters, judge assignments, round panels, entry-scoped ballot observations and event result sets. These are observations of one published tournament at capture time. Coverage can differ by tournament and publication settings.

A warehouse can answer who was listed, which entries were paired and which judges were assigned where the evidence supports those links. Public evidence does not establish complete ballot access, verified debate winners, stable cross-tournament student identity or judge paradigms. Harvard round 1587204, panel 9200905, still has an unresolved winner. Judge 2912715 explicitly maps to person 366665.

Dennis's next modeling decision is to approve the grain and keys for a normalized participation model. Start with tournament, event, tournament school, entry, student reference, tournament judge, round and panel, with explicit roster and assignment relationships. Model publication, raw ballot scores and standings as source observations. Reserve decision facts until side, score, vote aggregation, bye and forfeit semantics are verified. Warehouse implementation is outside TASK-009.

| /categories and /categories/*/events | Available structured public data in invite and bulk. Local category id/abbr/name/settings and event id/abbr/name/type/fee. | Tournament → category → event. Event is the competition division. NSDA category is a separate reference. |

School id/name/code, bulk chapter; entry id/name/code, active/waitlist, bulk dropped/unconfirmed/hybrid flags. | Tournament school ID differs from chapter ID. | /schools/*/students and /schools/*/entries/*/students | Available structured public data in field and bulk. ## Provenance and replay

Keep immutable authorized JSON bytes under controlled access with UTC capture time, full sanitized URL, request scope, HTTP status and media type, response SHA-256, parser version and OpenAPI version/digest. Hashes for this run were tournament `bd303042b4f98a9066c95dbcdba9b29a5021da10799dc3ad2913523d741fbdcd`, invite `1ef86551d4f5f261ac39c5ab2f1c7846cc26628e6147ef173bced83931b0e965`, field `725bfa7078653ac2349b4fa3da3c1bd8b01dd7b1f21a0598e94973e7826a1d04`, bulk `2a5c6c919883184bb22439cdf5e425001997aed337c1b9c19a18cc3e8e12d24c`. Published replay uses the existing [allowlisted Harvard projection](../../fixtures/tabroom/harvard-40923/provenance.json) and synthetic extensions of verified shapes. The live responses contain personal data and are excluded from the repository. Row-level provenance connects source method, source ID, JSON pointer and snapshot. Retain both observations when sources disagree. Visibility, missingness and parse failures need separate treatment from ordinary empty data.

TASK-002 already normalized the Harvard matchup, judge-person link and unresolved outcome; it had no normalized student roster or timeslot collection and read scalar score rather than the observed scores array. The proposed adapter extension adds student references, explicit entry roster observations, standalone timeslots and raw score arrays. Invitation configuration, result sets and other fields in the matrix are assessable in source snapshots; they are not all normalized outputs. The [first-party exporter](https://github.com/speechanddebate/tabroom/blob/master/web/api/download_data.mhtml) documents publication-dependent export branches. Use the live response and replay to assess any particular tournament.
